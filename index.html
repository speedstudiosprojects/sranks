SRanks

Rankups y prestigios para Spigot/Paper con una GUI totalmente configurable, requisitos combinables y recompensas reales. Un solo JAR desde 1.7.10 hasta 26.x.

Visión general

Todo lo que puedes hacer

SRanks no es solo una lista de rangos: es un sistema de progresión completo, pensado para que un administrador pueda ajustar cada detalle sin tocar Java.

01

Un JAR para todo

Bytecode Java 8 y capa de compatibilidad para arrancar en 1.7.10, 1.8.8, 1.21.x y 26.x sin builds separados.

02

Rangos y prestigios

Progresión ordenada, grupos de Vault, rango inicial, reset de prestigio y detección por datos, Vault o permisos.

03

Requisitos combinables

Dinero, tiempo de juego, XP, ítems, permisos y PlaceholderAPI. Se pueden combinar y consumir al subir.

04

Recompensas reales

Dinero, comandos de consola, ítems custom capturados de la mano, mensajes, broadcasts, títulos y action bar.

05

GUI configurable

Cabecera con tu rango actual, indicador de página, paginación, estados visuales, lore por estado, sonidos y botones.

06

Editor in-game

Recompensas, comandos, requisitos, apariencia de cada estado y selector de ítems con cabezas Base64.

07

Permisos y LuckPerms

Nodos claros, permiso por rango, editor separado y ejemplos de comandos para LuckPerms.

08

Rendimiento

Textos e ítems estáticos cacheados, E/S async, top con caché y nada de bucles innecesarios por tick.

Compatibilidad

Un JAR, muchas versiones

SRanks se compila contra la API de Spigot 1.16.5 pero genera bytecode Java 8. Las APIs posteriores se usan por reflexión y degradan si no existen.

EntornoEstadoQué se comprobó
Paper 1.7.10 + Java 8ProbadoArranque, configs, comandos, datos y `/rankup` dinámico.
Paper 1.8.8 + Java 8ProbadoGUI legacy, clics, paginación, editor, recompensas y prestigios.
Paper 1.21.4 + Java 21/26ProbadoGUI, Adventure, hex, PlaceholderAPI, rankup y prestige.
Paper 26.3 + Java 25/26ProbadoCarga, comandos, `/rankup`, Adventure y Materiales modernos.
Spigot 1.7.10 – 1.21.xSoportadoMisma API usada; solo APIs presentes en 1.7.10.
Spigot/Paper 26.xSoportadoDetección tolerante a versiones como `26.3.build.231-stable`.
Java

El JAR apunta a Java 8. Los servidores 1.7.10–1.21.x pueden usar Java 8 o superior; los servidores 26.x requieren Java 25+. Para compilar hace falta JDK 21+.

Primeros pasos

Instalación en 5 minutos

Compila o descarga el JARmvn clean package o usa SRanks-1.0.0.jar.
Cópialo a plugins/Arranca el servidor una vez para generar los archivos.
Instala dependencias opcionalesVault + economía para dinero/grupos; PlaceholderAPI para placeholders; LuckPerms para permisos.
Edita los YAMLEmpieza por rankups.yml, gui.yml y messages.yml.
Recarga y pruebaEjecuta /sranks reload y luego /sranks gui o /sranks rankup.

Archivos que se crean

messages.ymlTodos los mensajes, títulos, action bars y textos del editor.

Actualizar desde otra versión

Los archivos existentes no se sobrescriben. Si vienes de una versión anterior, añade manualmente el bloque commands.rankup-command a tu config.yml. Los mensajes nuevos del editor se rellenan automáticamente desde los defaults del JAR.

Comando opcional /rankup

Pensado para jugadores acostumbrados a Rankup3. Se registra dinámicamente y solo si el nombre está libre; SRanks no reemplaza el comando de otro plugin.

YAML
commands:
  rankup-command:
    enabled: true
    root: rankup   # rankup = intenta subir; gui = abre la GUI
  • /rankup sin argumentos ejecuta la acción de root.
  • Subcomandos: gui, rankup, ranks, prestiges, prestige, info, top, reload, set, reset, editor, help.
  • Por defecto está desactivado. Si otro plugin ya usa /rankup, se avisa y no se toca.
  • /sranks y /sr siguen funcionando siempre.
Seguridad

Permisos y LuckPerms

Los permisos están declarados en plugin.yml. El permiso explícito de un rango se exige siempre; el toggle global solo activa el nodo automático.

NodoDefaultUso
sranks.usetrueComandos básicos, GUI, rankup, prestige e info.
sranks.adminopReload, set, reset y bypass del editor.
sranks.admin.editoropEditor in-game de recompensas/requisitos.
sranks.topopConsultar la clasificación.
sranks.rankup.<id>opcionalPermiso automático si el rango no define uno y el toggle está activo.

Con LuckPerms

BASH
lp user Nombre permission set sranks.use true
lp user Nombre permission set sranks.admin.editor true
lp group admin permission set sranks.admin true
lp user Nombre permission set sranks.rankup.avanzado true
Permiso por rango

El campo permission: de un rango se exige siempre, aunque require-rank-permission esté en false. Si el rango no define permiso y el toggle está en true, se exige sranks.rankup.<id>. Puedes editar el nodo desde el editor in-game, pero el permiso real se concede en LuckPerms.

LuckPermsPermissionsEx Cualquier plugin de permisosOP para el editor
Progresión

Rangos y prestigios

El orden de los rangos se define con order. Si se omite, se usa el orden del archivo. Los prestigios se definen como una lista y su nivel es la posición.

Ejemplo de rango

YAML
ranks:
  aprendiz:
    order: 1
    group: aprendiz
    display-name: "<gradient:#A0A0A0:#FFFFFF><bold>Aprendiz</bold></gradient>"
    permission: ""            # opcional; si se define, se exige siempre
    requirements:
      money: { amount: 1000, take: true }
      playtime: { minutes: 30 }
    rewards:
      money: 250
      commands:
        - "say {PLAYER} ha ascendido de {OLD_RANK} a {RANK}."
      message: "<green>¡Has subido a <bold>{rank}</bold>!</green>"
    gui-item:
      material: LEATHER_CHESTPLATE

Campos de un rango

CampoDescripción
orderOrden numérico. Menor = antes.
groupGrupo de Vault al que se cambia. Por defecto, el id.
display-nameNombre visible con formato MiniMessage/legacy.
permissionPermiso opcional. Si existe, se exige siempre para subir.
requirementsRequisitos combinables (dinero, tiempo, XP, ítems, permiso, placeholder).
rewardsDinero, comandos, ítems, mensaje, broadcast.
gui-itemOverride opcional del ítem de la GUI para ese rango.

Ejemplo de prestigio

YAML
require-max-rank: true

prestiges:
  - id: prestige_1
    display-name: "<gradient:#FFD700:#FFAA00><bold>✦ Prestigio {level} ✦</bold></gradient>"
    reset-rank: aprendiz
    requirements:
      money: { amount: 100000, take: true }
      playtime: { hours: 5 }
    rewards:
      money: 25000
      commands:
        - "say {PLAYER} alcanzó el prestigio {PRESTIGE}. Vuelve a {RANK}."
      message: "<gold>¡Prestigio {prestige}!</gold>"

Detección del rango

ModoComportamiento
dataManda el rango guardado en playerdata. Recomendado.
vaultAl entrar se sincroniza con el grupo primario de Vault.
permissionAl entrar se busca el rango más alto cuyo permiso tenga el jugador.
Vault y grupos

La sincronización de grupo depende de que el proveedor de permisos de Vault implemente grupos. Si no lo hace, usa comandos de recompensa: lp user {PLAYER} parent set {RANK}.

Configuración

Requisitos

Se combinan todos los requisitos definidos. Cada uno muestra su progreso y puede consumir el recurso al subir si take: true.

YAML
requirements:
  money:
    amount: 7500
    take: true
  playtime:
    hours: 2
  xp:
    levels: 5
    take: true
  items:
    take: true
    list:
      - material: DIAMOND
        amount: 8
      - material: EMERALD
        amount: 4
        data: 0
  permission: "sranks.extra.vip"
  placeholder:
    placeholder: "%statistic_hours_played%"
    operator: ">="
    value: "10"

Tipos disponibles

TipoCamposConsumo
moneyamount, takeVault: retira el dinero.
playtimeseconds, minutes, hours, days, time: "2h30m"No aplica.
xplevels, points, amount + mode, takeNiveles o XP.
itemslist de material, amount, data, name, takeRetira los ítems.
permissionCadena o lista de nodosNo aplica.
placeholderplaceholder, operator, valueNo aplica.
Detalles

playtime se mide desde la instalación del plugin. Un número suelto se interpreta como minutos. En xp, un número suelto es niveles; usa points para XP total. Los ítems aceptan "DIAMOND:8" o mapas. Todos los requisitos aceptan name: para personalizar su etiqueta.

Operadores de placeholder

OperadorSignificado
>=, >, <=, <Comparación numérica si el valor es numérico.
==, equalsIgualdad de texto (sin distinguir mayúsculas).
!=Desigualdad.
containsEl valor contiene el texto esperado.

Formato lista

También se admite una lista de mapas con type:

YAML
requirements:
  - type: money
    amount: 1000
  - type: playtime
    minutes: 30
  - type: items
    take: true
    list:
      - material: DIAMOND
        amount: 8
Configuración

Recompensas

Las recompensas se ejecutan al subir de rango o prestigiar. Cada bloque está aislado: si un ítem o comando falla, los demás siguen ejecutándose.

YAML
rewards:
  money: 1500
  commands:
    - "say {PLAYER} ha subido de {OLD_RANK} a {RANK}."
    - "lp user {PLAYER} parent set {RANK}"
  items:
    - material: NETHER_STAR
      amount: 2
      name: "<gold>Recompensa</gold>"
      lore:
        - "<gray>Un premio por tu esfuerzo.</gray>"
      glow: true
      custom-model-data: 100
  message: "<green>¡Ahora eres <bold>{rank}</bold>!</green>"
  broadcast: "<gradient:#FFD700:#FF8C00>✦ {PLAYER} alcanzó {rank}.</gradient>"

Campos de ítem

CampoDescripción
materialMaterial moderno o legacy. Se mapea automáticamente.
amountCantidad; se reparte en stacks de 64 si hace falta.
dataData value legacy (1.7–1.12).
name, loreTexto con formato y placeholders.
custom-model-dataCustomModelData en 1.14+.
glowBrillo falso; se oculta si la versión lo permite.
skull-ownerNombre del jugador para cabezas.
enchantmentsLista de ENCHANT:level.
skull-base64Textura de cabeza en Base64.
serializedÍtem exacto serializado (lo genera el editor).
Dinero y Vault

Las recompensas de dinero requieren Vault y una economía. Si no hay proveedor, se avisa en consola y se omiten solo esas recompensas; los comandos y los ítems se entregan igual.

Placeholders de recompensa

PlaceholderValor
{PLAYER}Nombre del jugador.
{RANK} / {OLD_RANK}Grupo de Vault del rango nuevo/anterior.
{rank} / {old_rank}Nombre visible del rango nuevo/anterior.
{RANK_DISPLAY} / {RANK_ID}Nombre visible / id del rango.
{PRESTIGE} / {OLD_PRESTIGE}Nivel de prestigio nuevo/anterior.

Los comandos aceptan una cadena o una lista. Los ítems aceptan un mapa o una lista. Los ítems custom capturados desde el editor conservan nombre, lore, NBT, custom model data y encantamientos para la misma versión del servidor.

Cabecera y páginas

El slot 4 muestra TU RANGO ACTUAL con rango, siguiente, progreso, tiempo jugado, prestigio y página. El slot 8 muestra Página X/Y; las flechas 48/50 cambian de página y los rangos se reparten automáticamente entre rank-slots. En instalaciones antiguas, si page-info no existe, SRanks lo añade en memoria sin tocar tu gui.yml.

Variantes por estado

Cada ítem de la plantilla puede cambiar material, nombre, lore y cabeza según el estado. El editor in-game escribe estas claves:

YAML
items:
  next-rank:
    material-by-status:
      current: NETHER_STAR
      available: EMERALD
      locked: COAL
      unlocked: IRON_INGOT
      future: STONE
    name-by-status:
      current: "<green>Tu rango actual</green>"
      available: "<gold>Siguiente rango</gold>"
    lore-by-status:
      current:
        - "<gray>Este es tu rango actual.</gray>"
    skull-base64-by-status:
      current: "eyJ0ZXh0dXJlcyI6..."
    serialized-by-status:
      current:
        ==: org.bukkit.inventory.ItemStack
        type: PLAYER_HEAD
    glow-when: [current, available]

Reglas de la plantilla

  • Un ítem sin slot es la plantilla que se replica en rank-slots.
  • Un ítem con slot es fijo (cabecera, botón, cierre, etc.).
  • Los slots de contenido se paginan automáticamente según rank-slots.
  • Los botones de página se ocultan en la primera/última página.
  • Puedes sobrescribir la plantilla de un rango con gui-item en rankups.yml.

Flujo rápido

Abre el editorCon un jugador con permiso: /sranks editor.
Elige rango o prestigioLa lista está paginada automáticamente.
Edita recompensasPincha en Recompensas. Para comandos e ítems entra en sus pantallas específicas.
Añade ítems desde la mano o la GUIEl selector abre un espacio central para colocar el ítem; guarda una copia exacta y devuelve el original.
Personaliza la aparienciaEn Apariencia elige el estado (actual, siguiente, bloqueado, superado...) y cambia su ítem, nombre, lore o cabeza Base64.
Prueba y ajustaEl botón “Probar recompensas” ejecuta dinero/ítems/comandos sobre ti.

Prompts de chat

Los textos se piden por chat para evitar límites de la GUI. Se validan antes de guardar y hay un tiempo máximo de 120 segundos por prompt. Puedes escribir cancelar para salir sin cambios.

Cabezas Base64 y ítems custom

En la pantalla de apariencia, el botón Cabeza Base64 pide el código de textura. El chat de 1.7/1.8 limita a 100 caracteres, así que el editor acepta el código en varias partes y lo une; escribe fin al terminar. En versiones modernas se usa PlayerProfile; en 1.7–1.16 se aplica con GameProfile por reflexión. También puedes colocar una cabeza custom en el selector y se guarda su NBT exacto.

YAML
gui-item:
  skull-base64-by-status:
    current: "eyJ0ZXh0dXJlcyI6..."
  serialized-by-status:
    current:
      # ítem exacto con nombre, lore, NBT y comandos
      ==: org.bukkit.inventory.ItemStack
      type: PLAYER_HEAD

Overrides: editor.yml

El editor no reescribe rankups.yml ni prestiges.yml. Guarda solo los campos modificados en editor.yml, que se aplica después del YAML base. Así se conservan comentarios y el resto de la configuración.

YAML
ranks:
  aprendiz:
    rewards:
      money: 1234.0
      commands:
        - "say {PLAYER} ha subido a {RANK}."
      items:
        - material: DIAMOND_SWORD
          amount: 1
          name: "<gold>Espada del aprendiz</gold>"
          glow: true
          serialized:
            type: DIAMOND_SWORD
            meta:
              display-name: "§r§6Espada del aprendiz"
prestiges:
  prestige_1:
    rewards:
      money: 7777.0
Alcance del editor

El editor edita rangos/prestigios existentes, sus requisitos, recompensas, comandos, ítems y metadatos. No crea/elimina rangos, no cambia la disposición de gui.yml, no edita messages.yml ni los ajustes globales de config.yml. Eso sigue siendo YAML para no romper el diseño.

Si quieres volver al YAML base, usa “Restablecer override” en el editor de ese rango o prestigio. Los cambios se aplican al instante y persisten tras reiniciar el servidor.

PAPI en 26.3

Algunas versiones antiguas de PlaceholderAPI (por ejemplo 2.11.6) fallan al arrancar en 26.3 por su propio parser de versión. SRanks lo detecta y sigue funcionando sin PAPI. Usa una build de PlaceholderAPI compatible con tu servidor.

Mensajes

messages.yml está agrupado por contexto: general, rankup, prestige, info, ranks, prestiges, top, help, admin, gui y editor. Los títulos y action bars de rankup/prestige también se configuran ahí. Si una clave falta, se usa el default del JAR; nunca se sobrescribe tu archivo.

Precedencia de overrides

Si un rango tiene una entrada en editor.yml, sus campos mandan sobre rankups.yml. Para volver al YAML base, usa “Restablecer override” en el editor o elimina la entrada de editor.yml y ejecuta /sranks reload.

Integraciones

Vault y progreso del jugador

Vault es opcional, pero aporta dinero para requisitos/recompensas y, si el proveedor lo permite, cambio de grupo al subir de rango.

FunciónComportamiento
DineroRequisitos y recompensas usan la economía registrada en Vault.
GruposCon vault.sync-group: true, cambia el grupo primario al subir.
Detecciónrank-detection.mode: vault sincroniza al entrar con el grupo primario.
FallbackSi el proveedor no soporta grupos, usa comandos de recompensa.
YAML
# Si tu proveedor de Vault no cambia grupos, esto es 100% fiable:
rewards:
  commands:
    - "lp user {PLAYER} parent set {RANK}"
Proveedores de grupos

LuckPerms suele funcionar mediante Vault, pero algunos setups no registran el proveedor de grupos. SRanks detecta hasGroupSupport(); si no está disponible, no rompe el rankup: solo omite el cambio de grupo y deja que tus comandos lo hagan.

Tiempo de juego

  • SRanks mide el tiempo por sí mismo: sesión actual + acumulado persistido.
  • No usa estadísticas de vanilla que cambiaron de nombre en 1.13.
  • Se consolida cada settings.playtime-tick-seconds.
  • Se guarda cada settings.autosave-minutes, al salir, al subir y al apagar.
  • El tiempo empieza a contar desde la primera sesión que ve SRanks.

Datos y top

Cada jugador tiene un YAML en playerdata/<uuid>.yml con rango, prestigio y segundos jugados. El top lee esos archivos de forma async y cachea el resultado. Los datos de jugadores online se superponen al archivo para que el top esté actualizado.

Transparencia

Limitaciones reales

Estas son las restricciones que debes conocer antes de montar el plugin en producción. Están documentadas para evitar sorpresas.

!

Dinero y Vault

Las recompensas/requisitos de dinero necesitan Vault y una economía. Sin proveedor, se avisa y se omiten solo esas partes.

!

Grupos de Vault

El cambio de grupo depende del proveedor. Si no implementa grupos, usa comandos de recompensa (LuckPerms, etc.).

!

Ítems serializados

El editor guarda el ítem exacto para la misma versión del servidor. Para portabilidad entre versiones, usa comandos.

!

Alcance del editor

No crea/elimina rangos, no edita gui.yml, messages.yml ni la config global. Eso sigue en YAML.

!

1.7 y formato

Sin hex ni Adventure. Los gradientes degradan al primer color. El glow muestra encantamiento porque no existe ItemFlag.

!

Títulos largos

El cliente limita la longitud visible del título de inventario. Usa títulos cortos y placeholders compactos.

!

Requisitos de ítems

Se comparan por material y data. No se exige nombre/NBT exacto; para eso usa un requisito de placeholder.

!

PlaceholderAPI en 26.3

Algunas versiones antiguas de PAPI fallan al arrancar en 26.3 por su propio parser. SRanks sigue sin PAPI.

Más notas

Playtime: no importa estadísticas históricas de vanilla; empieza con SRanks. Top: lee YAML en async y cachea; para redes muy grandes, una base de datos sería el siguiente paso. /rankup: si otro plugin ya usa ese nombre, SRanks no lo pisa. PAPI 26.3: usa una build compatible. 1.7: el servidor debe correr Java 8+; el JAR es bytecode 8.

Ayuda

Preguntas frecuentes

He subido de rango pero no me han dado el dinero.

Revisa que Vault esté instalado y que exista un proveedor de economía. Si no lo hay, SRanks avisa en consola y omite solo el dinero; los comandos/ítems sí se entregan. Con Vault activo, comprueba que la cantidad sea mayor que 0.

No existe /rankup.

Por defecto está desactivado. Añade commands.rankup-command.enabled: true a config.yml y ejecuta /sranks reload. Si otro plugin ya usa /rankup, SRanks no lo reemplaza; usa /sranks.

El editor no guarda mis cambios.

Comprueba que tienes sranks.admin.editor o sranks.admin. Los cambios se guardan en editor.yml; si el archivo no es escribible, revisa permisos. Después de guardar, SRanks recarga el rank manager automáticamente.

¿Dónde están los cambios del editor?

En plugins/SRanks/editor.yml. Es una capa de overrides para no destruir los comentarios de rankups.yml/prestiges.yml. Para volver al YAML base, usa “Restablecer override”.

¿Cómo doy permisos con LuckPerms?

Usa los nodos de la sección Permisos. Por ejemplo: lp user Nombre permission set sranks.use true y lp user Nombre permission set sranks.admin.editor true. El permiso por rango se concede con el nodo configurado en el rango o con sranks.rankup.<id>.

¿Por qué no aparecen los mensajes nuevos?

Los archivos existentes no se sobrescriben. SRanks combina los defaults del JAR para las claves que falten en messages.yml. Si una clave no aparece, revisa que el YAML no esté corrupto y ejecuta /sranks reload.

¿Cómo cambio la GUI?

Edita gui.yml: título, filas, relleno, borde, sonidos, rank-slots, plantillas y botones. Los ítems sin slot son plantillas; los que tienen slot son fijos. Puedes sobrescribir la plantilla de un rango con gui-item.

¿Cómo hago que un ítem custom se entregue como recompensa?

El editor in-game tiene “Añadir ítem de la mano”. Guarda el ítem serializado (nombre, lore, NBT, custom model data, encantamientos). Para configurarlo a mano, usa items: con material, amount, name, lore, etc.

¿Por qué PAPI no resuelve placeholders?

Comprueba que PlaceholderAPI esté instalado y que compat.placeholderapi-in-text esté en true. En 26.3, algunas versiones antiguas de PAPI fallan por su propio parser; usa una build compatible.
